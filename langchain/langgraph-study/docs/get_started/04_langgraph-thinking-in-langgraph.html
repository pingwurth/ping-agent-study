LangGraph 中的思维方式

了解如何使用 LangGraph 构建智能体（Agent）的思维方式

在使用 LangGraph 构建智能体时，用户将其分解为称为节点（node）的离散步骤，描述节点之间的转换，并通过节点读写的共享状态（state）将它们连接起来。本指南将引导你构建一个客户支持邮件智能体。

从你要自动化的过程开始

首先描述你要构建的内容。将其写成自然语言、流程图或任何对你有用的形式。关键是先思考流程，再思考代码。

以下是一个客户支持邮件智能体的需求示例：

该智能体应该：

  • 读取收到的客户邮件
  • 按紧急程度和主题进行分类
  • 搜索相关文档以回答问题
  • 草拟适当的回复
  • 将复杂问题升级给人类客服
  • 需要时安排后续跟进

需要处理的场景示例：

  1. 简单的产品问题："如何重置密码？"
  2. Bug 报告："选择 PDF 格式时，导出功能会崩溃"
  3. 紧急账单问题："我的订阅被扣了两次费！"
  4. 功能请求："能否在移动端应用中添加深色模式？"
  5. 复杂技术问题："我们的 API 集成间歇性出现 504 错误"

要在 LangGraph 中实现智能体，用户通常遵循以下五个步骤。

步骤 1：将工作流拆分为离散步骤

每个独立的步骤成为一个节点（一个执行特定任务的函数），然后勾勒出这些步骤之间的连接方式。

流程图

显示邮件智能体工作流的节点和连接

箭头显示可能的路径；决定走哪条路径的决策发生在每个节点内部。

节点说明

Read Email（读取邮件）

提取并解析邮件内容

Classify Intent（意图分类）

使用 LLM 对紧急程度和主题进行分类，然后路由到适当的操作

Doc Search（文档搜索）

查询知识库以获取相关信息

Bug Track（Bug 追踪）

在追踪系统中创建或更新工单

Draft Reply（草拟回复）

生成适当的回复

Human Review（人工审核）

升级给人工客服进行审批或处理

Send Reply（发送回复）

发送邮件回复

提示：某些节点会决定下一步去哪里（Classify Intent、Draft Reply、Human Review），而其他节点总是继续到相同的下一步。

步骤 2：确定每个步骤需要做什么

对于每个节点，确定其操作类型以及需要哪些上下文。LangGraph 中的节点处理四种主要类型的操作。在设计智能体时，请考虑每个步骤属于哪种类型。

步骤类型

🧠

LLM 步骤

需要理解、分析、生成文本或进行推理决策时使用

🗄

数据步骤

需要从外部源检索信息时使用

⚡

操作步骤

需要执行外部操作时使用

👤

用户输入步骤

需要人工干预时使用

LLM 步骤

意图分类

  • 静态上下文（提示词）：分类类别、紧急程度定义、响应格式
  • 动态上下文（来自状态）：邮件内容、发件人信息
  • 期望结果：确定路由的结构化分类

草拟回复

  • 静态上下文（提示词）：语气指南、公司政策、回复模板
  • 动态上下文（来自状态）：分类结果、搜索结果、客户历史
  • 期望结果：可供审核的专业邮件回复

数据步骤

文档搜索

  • 参数：根据意图和主题构建的查询
  • 重试策略：是，使用指数退避处理瞬时故障
  • 缓存：可以缓存常见查询以减少 API 调用

客户历史查询

  • 参数：来自状态的客户邮箱或 ID
  • 重试策略：是，但在不可用时回退到基本信息
  • 缓存：是，使用生存时间（TTL）平衡新鲜度和性能

操作步骤

发送回复

  • 何时执行节点：在审批后（人工或自动）
  • 重试策略：是，使用指数退避处理网络问题
  • 不应缓存：每次发送都是唯一操作

Bug 追踪

  • 何时执行节点：当意图为 "bug" 时始终执行
  • 重试策略：是，确保不丢失 Bug 报告至关重要
  • 返回：工单 ID，用于包含在回复中

用户输入步骤

人工审核节点

  • 决策上下文：原始邮件、草拟回复、紧急程度、分类结果
  • 期望输入格式：审批布尔值加可选的编辑后回复
  • 触发时机：高紧急度、复杂问题或质量问题

步骤 3：设计你的状态

状态是所有节点都可以访问的共享内存。可以将其想象为智能体用来跟踪它学到和决定的一切的笔记本。

什么属于状态？

  • 包含在状态中："它是否需要跨步骤持久化？如果是，它就属于状态。"
  • 不存储："你能从其他数据派生它吗？如果是，需要时再计算。"

对于邮件智能体，需要跟踪以下内容：

  • 原始邮件和发件人信息（无法稍后重建）
  • 分类结果（多个下游节点需要）
  • 搜索结果和客户数据（重新获取成本高）
  • 草拟回复（需要在审核过程中持久化）
  • 执行元数据（用于调试和恢复）
提示："一个关键原则：你的状态应该存储原始数据，而不是格式化文本。在节点内部需要时格式化提示词。"

这种分离意味着：

  • 不同的节点可以为自己的需求以不同方式格式化相同的数据
  • 更改提示词模板不需要修改状态 schema
  • 调试更清晰 — 你可以准确看到每个节点接收到的数据
  • 智能体可以演进而不破坏现有状态

状态定义代码

from typing import TypedDict, Literal

class EmailClassification(TypedDict):
    intent: Literal["question", "bug", "billing", "feature", "complex"]
    urgency: Literal["low", "medium", "high", "critical"]
    topic: str
    summary: str

class EmailAgentState(TypedDict):
    # 原始邮件数据
    email_content: str
    sender_email: str
    email_id: str

    # 分类结果
    classification: EmailClassification | None

    # 原始搜索/API 结果
    search_results: list[str] | None
    customer_history: dict | None

    # 生成的内容
    draft_response: str | None
    messages: list[str] | None

状态只包含原始数据 — 没有提示词模板、没有格式化字符串、没有指令。分类输出作为 LLM 返回的字典直接存储。

步骤 4：构建你的节点

每个步骤都实现为一个 Python 函数，它接收当前状态并返回对状态的更新。

正确处理错误

生产级智能体需要优雅地处理故障。LangGraph 在节点级别提供错误处理，因此你可以根据错误类型为每个操作配置适当的策略。

错误类型 谁来修复 策略 何时使用
瞬时错误（网络问题、速率限制） 系统（自动） 重试策略 通常重试后可恢复的临时故障
LLM 可恢复错误（工具故障、解析问题） LLM 将错误存储在状态中并循环回来 LLM 可以看到错误并调整其方法
用户可修复错误（信息缺失、指令不清） 人类 使用 interrupt() 暂停 需要用户输入才能继续
重试后的可恢复故障 开发者（声明式） error_handler 在重试耗尽后运行补偿/恢复分支
意外错误 开发者 让它们冒泡 需要调试的未知问题

from langgraph.types import Command


def execute_tool(state: State) -> Command[Literal["agent", "execute_tool"]]:
    try:
        result = run_tool(state['tool_call'])
        return Command(update={"tool_result": result}, goto="agent")
    except ToolError as e:
        return Command(
            update={"tool_result": f"Tool error: {str(e)}"},
            goto="agent"
        )

实现邮件智能体节点

读取和分类节点

from typing import Literal
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command, RetryPolicy
from langchain_openai import ChatOpenAI
from langchain.messages import HumanMessage

llm = ChatOpenAI(model="gpt-5-nano")

def read_email(state: EmailAgentState) -> dict:
    """提取并解析邮件内容"""
    return {
        "messages": [HumanMessage(content=f"Processing email: {state['email_content']}")]
    }

def classify_intent(state: EmailAgentState) -> Command[Literal["search_documentation", "human_review", "draft_response", "bug_tracking"]]:
    """使用 LLM 对邮件意图和紧急程度进行分类，然后相应路由"""
    structured_llm = llm.with_structured_output(EmailClassification)
    classification_prompt = f"""
    分析此客户邮件并进行分类：

    邮件：{state['email_content']}
    发件人：{state['sender_email']}

    提供分类，包括意图、紧急程度、主题和摘要。
    """
    classification = structured_llm.invoke(classification_prompt)

    if classification['intent'] == 'billing' or classification['urgency'] == 'critical':
        goto = "human_review"
    elif classification['intent'] in ['question', 'feature']:
        goto = "search_documentation"
    elif classification['intent'] == 'bug':
        goto = "bug_tracking"
    else:
        goto = "draft_response"

    return Command(
        update={"classification": classification},
        goto=goto
    )

搜索和追踪节点

def search_documentation(state: EmailAgentState) -> Command[Literal["draft_response"]]:
    """在知识库中搜索相关信息"""
    classification = state.get('classification', {})
    query = f"{classification.get('intent', '')} {classification.get('topic', '')}"

    try:
        search_results = [
            "Reset password via Settings > Security > Change Password",
            "Password must be at least 12 characters",
            "Include uppercase, lowercase, numbers, and symbols"
        ]
    except SearchAPIError as e:
        search_results = [f"Search temporarily unavailable: {str(e)}"]

    return Command(
        update={"search_results": search_results},
        goto="draft_response"
    )

def bug_tracking(state: EmailAgentState) -> Command[Literal["draft_response"]]:
    """创建或更新 Bug 追踪工单"""
    ticket_id = "BUG-12345"
    return Command(
        update={
            "search_results": [f"Bug ticket {ticket_id} created"],
            "current_step": "bug_tracked"
        },
        goto="draft_response"
    )

回复节点

def draft_response(state: EmailAgentState) -> Command[Literal["human_review", "send_reply"]]:
    """使用上下文生成回复并根据质量路由"""
    classification = state.get('classification', {})
    context_sections = []

    if state.get('search_results'):
        formatted_docs = "\n".join([f"- {doc}" for doc in state['search_results']])
        context_sections.append(f"相关文档：\n{formatted_docs}")

    if state.get('customer_history'):
        context_sections.append(f"客户等级：{state['customer_history'].get('tier', 'standard')}")

    draft_prompt = f"""
    为此客户邮件草拟回复：
    {state['email_content']}

    邮件意图：{classification.get('intent', 'unknown')}
    紧急程度：{classification.get('urgency', 'medium')}

    {chr(10).join(context_sections)}

    指南：
    - 保持专业和乐于助人
    - 解决他们的具体问题
    - 在相关时使用提供的文档
    """

    response = llm.invoke(draft_prompt)

    needs_review = (
        classification.get('urgency') in ['high', 'critical'] or
        classification.get('intent') == 'complex'
    )
    goto = "human_review" if needs_review else "send_reply"

    return Command(
        update={"draft_response": response.content},
        goto=goto
    )

def human_review(state: EmailAgentState) -> Command[Literal["send_reply", END]]:
    """使用 interrupt 暂停等待人工审核，并根据决策路由"""
    classification = state.get('classification', {})

    human_decision = interrupt({
        "email_id": state.get('email_id',''),
        "original_email": state.get('email_content',''),
        "draft_response": state.get('draft_response',''),
        "urgency": classification.get('urgency'),
        "intent": classification.get('intent'),
        "action": "请审核并批准/编辑此回复"
    })

    if human_decision.get("approved"):
        return Command(
            update={"draft_response": human_decision.get("edited_response", state.get('draft_response',''))},
            goto="send_reply"
        )
    else:
        return Command(update={}, goto=END)

def send_reply(state: EmailAgentState) -> dict:
    """发送邮件回复"""
    print(f"Sending reply: {state['draft_response'][:100]}...")
    return {}

步骤 5：将它们连接起来

现在将所有内容整合在一起。节点被连接成一个可工作的图。由于节点自行处理路由，因此只需要基本的边。要使用 interrupt() 实现人机交互，需要使用检查点器（checkpointer）进行编译。

图编译代码

from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import RetryPolicy

workflow = StateGraph(EmailAgentState)

workflow.add_node("read_email", read_email)
workflow.add_node("classify_intent", classify_intent)
workflow.add_node(
    "search_documentation",
    search_documentation,
    retry_policy=RetryPolicy(max_attempts=3)
)
workflow.add_node("bug_tracking", bug_tracking)
workflow.add_node("draft_response", draft_response)
workflow.add_node("human_review", human_review)
workflow.add_node("send_reply", send_reply)

workflow.add_edge(START, "read_email")
workflow.add_edge("read_email", "classify_intent")
workflow.add_edge("send_reply", END)

memory = MemorySaver()
app = workflow.compile(checkpointer=memory)

图结构是最小化的，因为路由通过 Command 对象在节点内部发生。每个节点使用类型提示（如 Command[Literal["node1", "node2"]]）声明它可以去往哪里。

试用你的智能体

创建智能体后，使用 流式传输（streaming）运行它以查看节点执行情况，并使用 中断（interrupts）进行人机交互审批。查看 API 参考了解 stream 和 stream_events 的完整详情。

from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class EmailState(TypedDict):
    email_content: str
    response_text: str | None


def human_review_node(state: EmailState):
    interrupt(
        {
            "approved": False,
            "edited_response": state.get("response_text") or "",
        }
    )
    return {"response_text": "placeholder"}


app = (
    StateGraph(EmailState)
    .add_node("human_review", human_review_node)
    .add_edge(START, "human_review")
    .add_edge("human_review", END)
    .compile(checkpointer=InMemorySaver())
)

initial_state = {
    "email_content": "I was charged twice for my subscription! This is urgent!",
    "response_text": "Draft response",
}

config = {"configurable": {"thread_id": "customer_123"}}
stream = app.stream_events(initial_state, config, version="v3")
_ = stream.output
print(f"human review interrupt:{stream.interrupts}")

human_response = Command(
    resume={
        "approved": True,
        "edited_response": "We sincerely apologize for the double charge. I've initiated an immediate refund...",
    }
)

resumed = app.stream_events(human_response, config, version="v3")
final_state = resumed.output
print("Email sent successfully!")

图在 interrupt() 处暂停，保存到检查点器，并等待。它可以稍后从停止的地方恢复。thread_id 将所有状态保存在一起以维护对话上下文。这使得人类审核者可以在几分钟或几天后批准或编辑回复 — 智能体将从完全相同的位置继续执行。

总结与后续步骤

在 LangGraph 中构建智能体遵循一个自然的模式：将工作流分解为离散步骤，设计共享状态，构建处理错误的节点，并将它们连接成一个图。

核心要点

🗄

分解为离散步骤

每个节点做好一件事，支持流式进度、带暂停/恢复的持久化执行，以及通过步骤间状态检查进行清晰调试。

🗄

状态是共享内存

存储原始数据而非格式化文本，这样不同的节点可以以不同方式使用相同的信息。

📝

节点就是函数

它们接收状态、执行工作并返回更新。当需要路由决策时，它们同时指定状态更新和下一个目的地。

⚠

错误是流程的一部分

瞬时故障进行重试，LLM 可恢复错误携带上下文循环回来，用户可修复问题暂停等待输入，意外错误冒泡处理。

👤

人工输入是一等公民

interrupt() 函数无限期暂停执行，保存状态，并从停止的地方恢复。与其他操作结合使用时，它必须放在最前面。

🗄

图结构自然涌现

定义基本连接，节点自行处理路由逻辑，实现显式和可追踪的控制流。

进阶考量：节点粒度权衡

信息：大多数应用可以跳过此部分，直接使用上面展示的模式。

在设计智能体时，一个关键决策是将工作流分解为多少个节点。虽然本指南展示了一种平衡的方法，但理解其中的权衡有助于你为特定应用做出正确的选择。

LangGraph 的持久化层在节点边界创建检查点。更小的节点意味着更频繁的检查点，以及故障时需要更少的重复工作。

邮件智能体如此分解的原因

  • 外部服务隔离：文档搜索和 Bug 追踪是独立的，因为它们调用外部 API，允许独立的重试策略。
  • 中间可见性：将 "意图分类" 作为独立节点，可以在操作前检查 LLM 决策。
  • 不同的故障模式：LLM 调用、数据库查询和邮件发送有不同的重试策略；独立节点允许独立配置。
  • 可重用性和测试性：更小的节点更容易独立测试和重用。

另一种有效的方法是将 "读取邮件" 和 "意图分类" 合并为一个节点，尽管这会牺牲检查能力，并在故障时重复两个操作。

应用级别的关注点（如缓存搜索结果）是节点函数内部的实现决策，而不是 LangGraph 框架特性。

性能考量：更多的节点并不意味着更慢的执行。LangGraph 默认通过异步持久化模式在后台写入检查点。其他选项包括 "exit" 模式（仅在完成时检查点）或 "sync" 模式（阻塞直到每个检查点写入完成）。

后续学习方向

  • 人机交互模式 — 工具审批、批量审批等模式
  • 子图 — 为复杂的多步骤操作创建子图
  • 流式传输 — 为用户提供实时进度
  • 可观测性 — 使用 LangSmith 进行调试和监控
  • 工具集成 — 网络搜索、数据库查询、API 调用
  • 重试逻辑 — 使用指数退避进行重试
